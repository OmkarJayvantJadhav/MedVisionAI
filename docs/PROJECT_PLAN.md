# MedVision AI — Project Plan

This is the single source of truth for building MedVision AI. Read it before
starting any task, and use it to settle decisions. If a situation is not
covered here, apply the **decision rules** (§2), make the call, and record it
in the **decision log** (§12).

---

## 1. Problem, objective and scope

### Problem

Skin cancer is curable when it is caught early, and most suspicious lesions are
first seen in primary care. There, a clinician decides which lesions to refer
to a dermatologist: too few referrals delay cancers, too many fill dermatology
waiting lists with benign lesions. Dermoscopy improves that decision but takes
training to read. Classifiers trained on dermoscopy images could support it,
but most published ones are not safe to use for it:

- they answer every image, including images that are not dermoscopy;
- they report accuracy, not how many cancers they miss or for whom;
- their percentages are raw scores, not calibrated probabilities;
- they answer with a single diagnosis instead of the referral question, so a
  top-1 "nevus" can hide a high combined probability of malignancy;
- they do not show what the model looked at.

### Users

| User | Use |
|---|---|
| General practitioners and primary-care nurses with a dermatoscope | Decide whether to refer a lesion |
| Teledermatology triage | Sort incoming dermoscopy images by urgency |
| Clinicians in training | Compare their reading with the model and its heatmap |
| Researchers and engineers | A reproducible, documented baseline |

The public is not a target user: self-checks need a dermatoscope, and ordinary
phone photos are refused.

### Objective

Build an **open, reproducible referral check** for dermoscopy images of a
single lesion. For each image it returns one answer, in this order of priority:
**refer** (possible malignancy), **unsure**, **no flag** or **not assessed**,
with calibrated probabilities and a heatmap. It supports the clinician's
referral decision and never makes a diagnosis; it is not a medical device and
has not been clinically validated, and it says so on every screen.

Success criteria, in priority order (a lower item never trades away a higher one):

| # | Objective | Success criterion |
|---|---|---|
| 1 | Catch cancers | Malignant-group recall ≥ 0.90 at the referral threshold, fitted on validation and reported on test, with the referral rate and precision it causes |
| 2 | Honest confidence | Calibration error (ECE) ≤ 0.05 after temperature scaling |
| 3 | Refuse what it cannot judge | ≥ 99% of non-dermoscopy images rejected while ≥ 98% of lesion images pass |
| 4 | No silent failures | Under blur, noise, compression and lighting changes, images are rejected rather than silently misread |
| 5 | Explain itself | A heatmap for every answer, equal to TensorFlow Grad-CAM (cosine ≥ 0.99) |
| 6 | Report its weaknesses | Robustness and subgroup results regenerated by `make evaluate` and published in the model card |
| 7 | Run anywhere | CPU-only inference in one container under 512 MB; no GPU, external calls or API keys |
| 8 | Classify well | Macro F1 ≥ 0.72 and melanoma top-1 recall ≥ 0.70, which also lowers the referral rate at the same recall |

### Scope

**In scope**

- Dermoscopy images of a single skin lesion (JPEG, PNG or WebP, ≤ 8 MB,
  longest side ≤ 4096 px).
- One decision: refer, unsure, no flag or not assessed.
- Supporting detail: calibrated probabilities for the 8 ISIC 2019 categories
  (actinic keratosis, basal cell carcinoma, benign keratosis, dermatofibroma,
  melanocytic nevus, melanoma, squamous cell carcinoma, vascular lesion), the
  combined malignancy probability against the referral threshold, a heatmap
  and a fixed template summary. The malignant group is melanoma, basal cell
  carcinoma, squamous cell carcinoma and actinic keratosis.
- Anonymous, stateless use; images are processed in memory and never stored.

**Out of scope**

| Excluded | Reason |
|---|---|
| Diagnosis, treatment or management advice | The output supports a referral decision; diagnosis belongs to the dermatologist |
| Self-checks by the public; ordinary phone and clinical photos | The model only learned from dermoscopy; other images are rejected (D45) |
| Rashes, infections, inflammatory and other non-lesion conditions | A different problem with different data (D53) |
| Rare skin cancers outside the 8 classes | No training data; a "no flag" answer never rules them out, and the model card says so |
| Text generated by a language model | Summaries come from a fixed template so they can never invent a claim (D51) |
| Accounts, patient records, stored images, mobile apps | No patient data is kept |
| Commercial use | The training data, and so the model weights, are licensed for non-commercial use |

### Infrastructure constraint

Every service runs on a free tier. This is a constraint on the design, not a
feature to advertise: public documents describe the tool, not its hosting bill.

| Need | Service | Limit that shapes the design |
|---|---|---|
| Training | Kaggle notebook, T4 GPU | About 30 GPU hours a week; a run must fit in one background session (≤ 12 h) |
| Model hosting | GitHub Releases | Versioned files with SHA-256 checksums, kept out of git |
| CI | GitHub Actions | Free for public repositories |
| Live app | Render free web service | 512 MB RAM, a fraction of one CPU, sleeps after 15 idle minutes |
| Data | ISIC 2019 (CC BY-NC 4.0), Open Images V4 (CC BY 2.0) | Model weights are CC BY-NC 4.0 |

## 2. Decision rules (apply in this order)

1. **Patient safety and correctness first.** Never ship a change that makes
   the system more confident or less honest. When in doubt, reject or flag
   low confidence instead of guessing.
2. **A working end-to-end tool beats a better model.** Do not tune the model
   while the API, UI, or deployment is broken.
3. **Tested and reproducible beats clever.** Every feature lands with tests.
   Every number in the README and model card must be reproducible by a script
   in the repo.
4. **Simple, boring, free.** CPU-only inference, free tiers, no API keys, no
   paid services. Prefer the standard library and well-known tools over new
   dependencies.
5. **The serving path never imports TensorFlow.** TensorFlow lives only in
   `ml/`. The backend runs on ONNX Runtime and NumPy.
6. **Small, reviewable changes.** One concern per commit and pull request.
   Don't mix refactors with behaviour changes.
7. **When two options are close, pick the one that is easier to explain in an
   interview**, and write down why.
8. **Stay in scope.** A feature must serve the objective in §1; anything in the
   out-of-scope table is declined, not half-built (D51).

## 3. Origin

The project grew out of a TensorFlow/Keras prototype (a skin, eye and oral
classifier trained on an undocumented dataset). Its training loop, Grad-CAM
reference and ONNX export idea were reused; its eye and oral models, dataset
and trained weights were not (D1, D21, D23). The prototype's numbers are not
comparable with this project's, because its data had no documented provenance
and was not checked for leakage.

## 4. Architecture

```
            offline (free Kaggle GPU)                       online (free Render CPU)
 ┌────────────────────────────────────────┐     ┌──────────────────────────────────────────┐
 │ ml/  TensorFlow                         │     │ one Docker container                     │
 │  prepare → split → check-leakage →     │     │  React app (static files)                │
 │  train → evaluate → calibrate →        │     │  FastAPI /api/v1                         │
 │  fit-ood (+ noise) → robustness →      │     │  ONNX Runtime + NumPy:                   │
 │  subgroups → export (parity-checked)   │     │   quality and noise checks →             │
 └───────────────────┬────────────────────┘     │   model → OOD distance → calibration →   │
                     │ GitHub release            │   safety rules → CAM heatmap             │
                     │ model.onnx, head_weights, │  no database, no external calls          │
                     │ ood_stats, model_meta     └───────────────────▲──────────────────────┘
                     └──────── downloaded and SHA-256 verified at image build ─┘
```

Details, module tables and the request sequence are in
[`architecture.md`](architecture.md).

### Key design: Grad-CAM without TensorFlow

The head is `GAP → Dropout → Dense`. For this head the Grad-CAM channel
weights for class *c* equal the Dense kernel column `W[:, c]` (divided by the
constant H·W), so Grad-CAM reduces to CAM:
`cam = ReLU(Σ_k W[k, c] · A_k)`, where `A` is the last feature map.

- The ONNX export has two outputs, `probabilities` and `feature_maps`
  (7×7×1280 for EfficientNet-B0), and the release ships `head_weights.npz`.
- The backend recomputes logits, the heatmap and the out-of-distribution
  distance from the one forward pass.
- A parity test fails the build if the NumPy heatmap drifts from TensorFlow
  Grad-CAM (cosine < 0.99). If the head ever changes shape, this shortcut must
  be revisited in §12.

## 7. API contract (v1)

All endpoints live under `/api/v1`. Errors use one body:
`{"error": {"code": "string", "message": "string"}}`. The full reference is
[`api.md`](api.md); the OpenAPI schema is committed in
`frontend/src/api/openapi.json` and a backend test fails if it is stale.

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness: `{"status": "ok"}` |
| GET | `/ready` | Model loaded and checksum-verified, with its version |
| GET | `/meta` | Model version, classes, malignant classes, fitted thresholds, upload limit, disclaimer |
| POST | `/predict` | Multipart `file`; prediction |
| POST | `/explain` | Same, plus heatmap and overlay PNGs (base64) |

A prediction contains `status` (`ok`, `low_confidence`, `rejected`),
`predicted_class`, `confidence`, `top_k`, `risk_flag`
(`malignant_suspected`, `benign`, `uncertain`), `malignant_probability`,
`reasons`, `model_version`, `calibrated`, `thresholds_fitted`, `summary`,
`disclaimer` and `latency_ms`.

Input limits: JPEG, PNG or WebP only, ≤ 8 MB, longest side ≤ 4096 px,
verified by decoding, not by file name. Uploaded images are **never written
to disk or logged**.

## 8. Safety and responsible-AI rules (non-negotiable)

1. Every response and every screen shows the disclaimer: decision support,
   not a diagnosis, not a medical device, not clinically validated; the
   referral decision rests with the clinician.
2. **Calibration:** temperature scaling fitted on validation, shipped in
   `model_meta.json`; ECE and reliability diagrams reported before and after.
   Target ECE ≤ 0.05.
3. **Rejection and low confidence (status field):**
   - `rejected`: the image fails a quality check (brightness, sharpness, sensor
     noise) or the out-of-distribution check on its features. Each fitted
     threshold lets 99% of validation images through and is reported on test
     and on a licensed set of everyday photos (D45, D47).
   - `low_confidence`: calibrated top probability below `τ`, fitted so
     confident answers are ≥ 85% accurate on validation (D41).
4. **Malignancy safety:** if the summed calibrated probability of the malignant
   group reaches `τ_malignant`, set `risk_flag = malignant_suspected` even when
   the top class is benign. `τ_malignant` gives malignant-group recall ≥ 0.90
   on validation; the resulting precision and referral rate are reported
   honestly. The interface calls this flag "refer".
5. **Model selection:** among candidates, choose by (a) malignant-group recall
   at the operating point, then (b) macro F1, then (c) ECE. Never by accuracy
   alone.
6. **Robustness and fairness reporting:** per-class metrics, silent misses
   under image corruptions, and results by sex, age and body site. Skin type is
   not recorded in the training data; the model card states that gap.
7. **Summaries only restate the model's output** from a fixed template: no
   generated text, no diagnosis, no treatment (D51).
8. Never publish a number that a script in the repository cannot reproduce.
9. **Answer order:** refer (malignancy flag), then unsure, then no flag. A
   warning is never hidden behind uncertainty, and a rejected image says what
   to fix.
10. **Wording addresses the clinician.** Answers suggest considering referral;
    they never tell a patient what they have or what to do (D53).

### Phase 9 — Stronger model

Runs on the free Kaggle GPU; each experiment is logged in MLflow and compared
with the §8.5 selection rule in an ablation table.

- [x] Training options, defaults unchanged (D55): full fine-tuning, focal
      loss, cosine schedule with warm-up, vertical flips, any rotation,
      brightness and saturation augmentation; an experiment switch in the
      Kaggle notebook; the ladder and results table in
      [`experiments.md`](experiments.md).
- [ ] Re-baseline the current recipe on the leakage-free splits.
- [ ] Larger backbones that keep the `pool → dense` head so CAM stays exact:
      EfficientNetV2-S, ConvNeXt-Tiny.
- [ ] Higher resolution (288 / 320 px), full fine-tuning, focal loss versus
      square-root class weights, stronger augmentation; test-time augmentation
      only within a CPU budget of ≤ 100 ms per image locally.
- [ ] Re-fit calibration and every gate, rerun `make evaluate`, and publish a
      new minor release only if the selection rule prefers it.
- **Targets:** macro F1 ≥ 0.72, melanoma top-1 recall ≥ 0.70,
  malignant-group recall ≥ 0.90 at `τ_malignant`, ECE ≤ 0.05, and a lower
  referral rate than model-v2.2.0 (49%) at that recall. These are goals, not
  claims: report what is achieved.

## 10. Conventions

**Code**
- Type hints everywhere; mypy strict for `backend/app` and `ml/src`.
- Google-style docstrings on public functions; no commented-out code.
- No global state with side effects at import time; configuration objects are
  created explicitly and injected (FastAPI dependencies for the backend).
- Raise specific exceptions; the API maps them to error codes in one place.
- Log with `logging` (JSON in the backend); never `print` outside CLIs.
- Constants such as class names come from `model_meta.json`, never
  hardcoded in several places.

**Tests**
- Every bug fix comes with a regression test.
- Markers: `data` (needs the dataset), `model` (needs real release files) and
  `slow`. CI excludes `data` and `model`. Parity tests build small models in
  memory, so they run in every CI run without downloading artifacts.

**Git**
- Branches: `feat/...`, `fix/...`, `chore/...`, `docs/...`; short-lived; merge
  to `main` with squash.
- Commit messages: Conventional Commits (`feat(api): add /explain
  endpoint`), imperative mood, body explains *why* when not obvious.
- Commit messages contain only the change description: **no co-author
  trailers, tool attributions, or generated-by footers.**
- Tracked files describe the project only. They do not reference the editors,
  assistants, or other tooling used to write them. Tool-specific config
  folders and files stay untracked.
- Never commit datasets, model binaries, `.env` files, MLflow runs, or
  generated outputs (except small curated figures under `docs/assets/`).

**Versioning**
- Model artifacts: `model-vMAJOR.MINOR.PATCH` release tags; any change to
  classes or input spec is a MAJOR bump.
- API: path-versioned (`/api/v1`); breaking changes need `/api/v2`.

## 11. Quality gates (CI must enforce)

- ruff, mypy, ESLint and Prettier clean.
- pytest (backend coverage ≥ 85%) and Vitest.
- Parity tests: ONNX vs Keras probabilities, NumPy CAM vs TensorFlow Grad-CAM,
  served resize, out-of-distribution distance and noise estimate.
- The Docker image builds, and a smoke test against the container checks
  `/ready`, the home page, `/predict`, `/explain`, rejection of a non-skin and
  a grainy image, and p95 latency (warning above 150 ms).
- The same smoke test runs daily against the live site.
